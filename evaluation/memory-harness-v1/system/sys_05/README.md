For every observed pair, processing_started must not follow applied or visible; existing applied<=visible and stage-prefix rules remain. Missing processing with observed application/publication stays null and adds explicit unknown-processing/incomplete evidence, disabling comparison readiness. No time is clamped or replaced by zero.

A v2 repair row retains the real nullable `blocked_ns` plus `observed_from_ns`, `observed_through_ns` and `end_state` (republished/still_blocked/unknown), in addition to validation/republish timestamps and validation hash. The two observation bounds must lie within the measurement window and be ordered. Known origin cannot follow first observation. Validation and republish must not follow the observed bound; a republished interval requires validation and a bound equal to republish. Future or wholly out-of-window records are rejected, not silently dropped. Nonnegative durations must fit signed int64; absolute timestamps can be negative or known zero.

For actual origin900, window start1000, validation1220 and republish1260, with observed bounds1000..1260, the full interval is360 and observed window outage is260. Origin900 is never rewritten to1000. `full_interval_ns` is exact only with known origin and republish. `full_observed_lower_bound_ns` is separate for an ongoing interval with known origin. `interval_window_overlap_ns` is the mathematical intersection of known full endpoints with the window; `observed_window_outage_ns` is the explicitly witnessed bound difference. If observation starts at1050 in that same interval, intersection260 and witnessed210 are both retained and coverage is incomplete.

Unknown origin yields null full duration/overlap/lower-bound fields; it does not yield zero. Unknown end or a shortened observation bound does not extend to the global horizon. A still-blocked interval observed through the horizon can completely cover that window while its final full duration remains right-censored/null. Empty intervals are not evidence of no repair; their observed-union is null, not known0. Missing origin/end or observation gaps are explicit incomplete coverage. Window union includes only witnessed intervals, with overlap counted once; queue delay remains separate. Legacy v1 repair rows lack explicit window witnesses, so remain labeled v1/incomplete for v2 comparison rather than being given fabricated carry-in provenance.

The summary has explicit machine-readable `comparison_profile` and `comparison_scope`. A valid legacy within-window reported run uses `reported_window_v1` / `legacy_within_window_reported_only`, preserving the original common-input, read freshness/quality and full-denominator conditions plus corrected processing causality. Its v1 repair fields do not become v2 carry-in/window witnesses; `v2_repair_coverage_ready` remains false. A v2 run uses `explicit_window_witness_v2` / `reported_explicit_window_witness_only` and additionally requires complete explicit repair coverage. Unknown v2 evidence stays v2/incomplete, never falls back to v1. Mixed profiles raise `comparison_profile_mismatch`. B requires the explicit v2 profile plus external entry gates and actual implementation; `B_execution_ready` is always false here. Legacy readiness does not mean v2 coverage, service performance, superiority or card acceptance.

The remaining interface and runtime boundaries below still apply, except for the explicitly versioned observation/summary changes above. Actual SYS03/04 integration, service performance and whole SYS05 acceptance remain pending.

## v3 fault-window comparison (`compare_v3.py`)

The v2 summary and compare are unchanged and still report a B pair as not ready: v2 counts a run with no repair interval as incomplete ("empty intervals are not evidence of no repair"), and sync never withholds, so it never has one. `compare_v3.py` (`sys05-comparison-eligibility-v3`) keeps every v2 readiness gate except repair coverage and the run's own last-observation time (summarize still refuses a run observed for less than the planned window), and asks each run for an explicit fault witness written by the measurement test (`fault_witnesses` in the raw run): the delete, one look at whether a read could select the snapshot (taken between two observations that must agree, else `unknown`), and the republication. The raw run is re-projected and must reproduce the ledger and observations byte for byte.

- `withheld`: the run must also have its one complete v2 repair interval with the same id, starting at or after the delete and containing the look, ending at the republication. The interval and the unwitnessed span before it are both reported.
- `behind`: not withheld, but a read gets no snapshot: the snapshot is not the current publication (the last applied update is not published), or none is available (not yet published or expired). No repair interval may exist.
- `servable`: a read could select a snapshot; its publication time must precede the delete, and no repair interval may exist.

The state is claimed only at the look (`state_scope: one_look_at_observed_ns`), not for the whole window. The delete-to-republication span, inside the planned window, is the one window common to both modes. A pair is comparable when both runs share the common inputs, differ in mode and are ready under these rules. Per-mode latencies, queue delay, freshness age, status counts, last costs and the fault window are reported side by side; `superiority_conclusion` stays `not_evaluated`.

Limit: the witness is written by the measurement test like the rest of the raw run. A withheld look is cross-checked against the repair interval the service recorded; a behind or servable look is checked only for order and consistency, so `execution_authenticated` stays false.

## Inputs and deterministic plans

All fields are required, including nullable observation fields. The contract's `schemas` are authoritative: `config`, `request`, `ledger`, and `observations`. Objects reject missing/unknown fields and wrong types. Integers are signed int64; counters/durations have the specified nonnegative/positive domains. Booleans are not integers. Duplicate JSON keys, floats/nonfinite numbers, malformed UTF-8/surrogates, excessive nesting and oversized input are rejected. Mechanical input bounds (64 MiB, depth 32, 4,096 UTF-8 bytes per string, 100,000 rows, 200,000 aggregate array entries) are parser safeguards, not service capacity settings.

The caller supplies seed, mode, scenario, cache condition, arrival segments, queue admission/batch/concurrency/retry/deadline limits, faults, allowed freshness, quality criterion hash, model hash and request corpus hash. Nothing supplies a product default. `start_ns` may be negative or zero; offsets/durations are integer nanoseconds on the caller's one clock. Checked window arithmetic must fit int64.

Each segment expands `count` requests at `start_ns + offset_ns + i*spacing_ns`, with an operation of read/update/privacy/embedding. The generator does not execute admission, retries, failure injection, queue behavior or publication. Normal/burst/overload are declared scenario labels; no throughput threshold is inferred. Restart/publish-delay/store-failure scenarios require the corresponding fault declaration; cold/warm scenarios require matching cache condition. Fault durations must fit the declared arrival window.

Request IDs and payload identities use the explicit hash domains in the contract. A sorted compact semantic config excluding only `mode` and `run_id` supplies the common-input hash. Request IDs include that hash, segment index and item index. Same-time requests sort by ID. Exact raw config bytes bind the workload's `config_sha256`; identical bytes always produce identical workload bytes and SHA. Different modes/run IDs retain the same logical request identities when all other inputs match. Payloads are hashes only, with no source text or query bodies.

## External ledger and observations

The workload is JSONL. The independently captured external received ledger is separate JSONL of `{protocol,request,received_ns}`, where `request` must exactly equal a generated request, including its config binding. Workload bytes must equal regeneration from the exact config. The tool never generates an external ledger or performance observations as a result of executing a plan. Tests create only explicitly synthetic observations.

No external ledger means failure. Duplicate/extra/mutated ledger records, duplicate/extra/conflicting outcomes, invalid stage order, mismatched config, impossible retry order or future snapshot are rejected. Missing ledger/outcome rows fail by default. `--allow-incomplete` explicitly reports missing IDs, retains the full planned/received denominators and disables comparison readiness. It does not invent pending or successful results for missing records.

One outcome belongs to one logical request. Attempts are contiguous, bounded by the caller's retry allowance, sequential and separately counted. Its last status must equal the logical status. Pending has no completion; a timeout may have no observed end, and no deadline latency is fabricated. `received_ns` comes from the external ledger. `accepted_ns` applies to every operation; durable/applied/visible stages apply to non-read operations. Later observed stages require earlier stages and monotone times. Null means unobserved/not claimed; success does not prove asynchronous visibility. Update-stage recovery gaps exclude reads.

A read uses `read_at_ns - snapshot_ns` for freshness. Snapshot age is distinct from response latency. Unknown freshness, violations, false/unknown quality, fallback unknown, timeout and failure remain visible. A reported quality boolean or validation hash is not authenticated quality, authorization, deletion or publication evidence.

The current wire is an **offline proposed adapter boundary**, not an existing SYS-03 receiptchain decoder. A future B owner must join actual request ingress identities, durable receipts and lifecycle observations into this exact ledger/outcome protocol while retaining raw provenance. This implementation does not fabricate that join, promote receipt metadata into request success, or claim that SYS-03/04 gates are met.

## Summary interpretation

Every summary is grouped by one mode/scenario/cache/run. Completed-response and success-only latency distributions are separate. Both include sample N, nearest-rank p50/p95/p99 (`ceil(p*N/100)-1`), minimum, maximum, and an exact mean encoded as quotient/remainder/denominator. Empty statistics are null, not zero. All statuses and censored/unobserved completion counts accompany those distributions. Throughput retains success numerator, all-planned denominator and observed elapsed nanoseconds; no success-only time denominator is substituted.

Queue samples report depth and oldest age separately, with unknown/missing coverage. A pre-existing backlog can be older than the run; age is not clamped. Known depth zero requires age zero. Queue delay comes from explicit enqueue/processing timestamps and is separate from repair serving outage. V2 repair intervals retain pre-window origins and explicit witnessed window bounds; republish requires a validation timestamp and hash. Both individual durations/window overlap and the witnessed-window union are reported. Still-blocked intervals extend only to their explicit bound. Missing intervals do not prove no repair. These observations do not execute a restore or prove safe serving.

Privacy and embedding coverage must each be represented. Unknown coverage cannot assert no starvation. These background observations are separate from logical request counts; this tool does not schedule jobs. State, receipt, ledger, checkpoint, replay, raw-source, log, database and RSS bytes each have independent sample/unknown/min/mean/max/last statistics. Independent peaks are not summed; small state is not a whole-system O(1) claim.

`compare(left_inputs,right_inputs)` revalidates both raw config/workload/ledger/observation tuples. It only marks input comparison readiness when common inputs, normalized request sequence, origin and observation duration match, modes differ, reconciliation is complete, all received reads have reported acceptable freshness and quality, processing order is known where applicable, and its explicit versioned profile requirements are met (v2 additionally requires repair window coverage). No read evidence is not readiness. Different budgets/freshness/quality/model/corpus/cache/scenario do not qualify. Failure/timeout/pending remain in each summary. Every comparison says `superiority_conclusion: not_evaluated` and `execution_authenticated: false`; it performs no effect-size, pilot, or scientific decision.

## Commands and publication

Use explicit absolute input/output paths. On POSIX, files/ancestors must not be symlinks; inputs must be regular files. Publication writes one new file using an exclusive hard-link commit after fsync; existing paths are never overwritten. This is a single-file atomic publication, not a multi-file transaction. Parent directories must already exist. CLI errors are fixed code/schema-path JSON, with no traceback, raw content or supplied path; dependency bootstrap errors are fixed `internal_error`.

```sh
python3 generate_workload.py --config /absolute/config.json --out /absolute/workload.jsonl
python3 summarize_load.py --config /absolute/config.json --workload /absolute/workload.jsonl --ledger /absolute/external-ledger.jsonl --observations /absolute/observations.json --out /absolute/summary.json
python3 measurement_adapter.py --config /absolute/config.json --workload /absolute/workload.jsonl --raw /absolute/raw-run.json --ledger-out /absolute/ledger.jsonl --observations-out /absolute/observations.json
python3 -m unittest discover -s evaluation/memory-harness-v1/system/sys_05 -p 'test_*.py'
```

`measurement_adapter.py` projects one raw B run (`sys05-b5-raw-run-v1`, written by the Go measurement test) onto this unchanged ledger and observation format. Times move to the run anchor; only observed stage prefixes are kept; background operations are refused; a repair interval needs a harness hold witness inside it. It changes none of the files above.

Error codes include `invalid_cli`, `invalid_json`, `invalid_unicode`, `duplicate_key`, `invalid_integer`, `invalid_number`, `invalid_type`, `invalid_value`, `invalid_fields`, `limit_exceeded`, `unsafe_path`, `io_error`, `contract_mismatch`, `time_overflow`, `invalid_schedule`, `missing_fault`, `invalid_cache`, `invalid_jsonl`, `invalid_time`, `invalid_attempts`, `conflicting_result`, `stage_gap`, `not_applicable`, `invalid_snapshot`, `duplicate_record`, `extra_record`, `request_mismatch`, `incomplete`, `invalid_backlog`, `missing_validation`, `incomplete_background`, `conflicting_coverage`, `workload_mismatch`, `missing_ledger`, `config_mismatch`, `comparison_profile_mismatch`, and `internal_error`.
