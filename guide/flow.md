# FLOW: 작업을 한곳에서 관리하고 결과 받기

FLOW는 기존 전문가·팀·자동화를 한 목록에서 관리합니다. 전문가와 팀의 별도 상위 메뉴를 합치며, 저장된 정의와 기능은 유지합니다. 작업별 실행·문맥·권한·예산은 각각 보관합니다.

이 문서는 2026-10-28 작업 브랜치의 동작과 지원 범위를 설명합니다. 공개 설치 파일이나 운영 서버에 반영됐다는 뜻은 아닙니다.

## 기존 기능의 위치

| 기능 | FLOW에서 여는 곳 |
|---|---|
| 전문가 만들기·편집, 역할·페르소나·모델·스킬·도구 | 새 작업 선택 또는 기존 전문가 항목의 설정 |
| 팀 구성·리더·회의 | 팀 항목의 설정과 실행, 회의 기록 탭 |
| 자동화·그래프·실행 이력 | 작업 항목의 자동화와 기록 |
| 전문가가 사용하는 그래프 | 해당 전문가의 작업 방식 설정 |
| 사용량 | 사용량 탭 |

전문가 소유의 그래프는 독립 작업 목록에 중복 노출하지 않습니다. 전문가를 통해 편집·호출합니다. 기존 전문가·팀의 `@이름`, 워크플로우의 `$이름` 호출은 유지하며, 독립 워크플로우는 사용 가능한 `@이름`으로도 호출할 수 있습니다. 이름이 충돌하면 기존 항목을 덮어쓰지 않습니다.

## 기존 리서치를 개선하기

1. FLOW에서 **리서치 열기**를 누르거나 새 작업에서 **리서치**를 선택합니다. 저장된 `리서치`가 있으면 먼저 그 항목을 엽니다.
2. **리서치 개선안 검토**를 누릅니다. 이 단계는 제안을 읽기만 합니다. 기존 모델·스킬·검색 연결·승인·예산과 그래프를 함께 검토합니다.
3. 기본 호출 이름과 **깊은 조사 @이름**을 확인합니다. 기본은 `@리서치`, 깊은 조사는 `@딥리서치`입니다. 다른 항목이 이미 그 이름을 사용하면 제안에 표시된 고유 별칭을 사용합니다.
4. **개선안 저장**을 눌러 적용합니다. 기존 항목의 ID와 읽은 revision을 사용해 수정합니다. 그사이 다른 곳에서 수정됐으면 충돌을 표시하므로 최신 내용을 다시 읽고 검토해야 합니다.

미리보기 API는 `GET /v1/crew/templates/research`입니다. 응답의 `existing_id`와 `expected_revision`이 있으면 기존 `POST /v1/crew/{id}`로 저장합니다. 목록 열기와 미리보기만으로 운영 정의가 바뀌지 않으며, 수정 실패를 새 항목 생성으로 대체하지 않습니다.

저장된 리서치가 없으면 기본 조사 템플릿을 미리 보고 **리서치 만들기**로 생성할 수 있습니다. 이 기본 템플릿에는 기존 다단계 리서치의 자동 심층 전환이나 깊은 조사 별칭이 없습니다. 화면에서 이를 구분해 안내합니다. 임의의 그래프를 보존할 수 없는 경우에도 개선안 API는 오류를 반환하며 다른 그래프로 교체하지 않습니다.

### 깊은 조사는 언제 시작하나요?

개선안을 저장한 리서치는 **확인한 출처와 남은 근거의 부족 여부**로 분기합니다. 경과 시간은 심층 전환의 판단 기준이 아닙니다. 시간·단계·예산 제한은 실행 한도로 별도로 유지합니다.

빠른 조사 보고서에 출처가 없거나 추가로 확인할 공개 근거가 남으면 기존 심화 경로로 이어집니다. 보고서의 `needs_more_evidence`와 `gaps`를 검사하며, 추가 필요 여부가 생략되고 gaps가 남아 있으면 보수적으로 추가 조사가 필요한 것으로 봅니다. 최종 단계까지 출처가 없거나 허용된 보완 뒤에도 필요한 근거가 부족하면 실패로 남깁니다.

`@리서치`와 깊은 조사 별칭은 **같은 저장 정의**를 실행합니다. 깊은 별칭으로 직접 요청하면 빠른 조사 구간을 건너뛰고 기존 심화 계획부터 시작합니다. **사람의 승인과 그 뒤 검색·검토 단계는 유지**하며, 심화 검색 직전에 저장된 승인 결정을 다시 확인합니다. 별도 딥리서치 항목을 자동 생성하거나 기존 딥리서치 항목을 덮어쓰지 않습니다.

모델이 근거 부족이나 비공개 여부를 잘못 판단할 가능성은 남습니다. 형식·출처 URL·분기 검사는 주장과 출처의 사실관계를 검증한 결과가 아닙니다.

## 에이전트 앱에서 최종 결과까지 받기

Arkism MCP가 연결된 활성 대화에서 `@리서치 조사할 주제`처럼 명시적으로 요청하거나, 에이전트가 저장된 작업을 선택해 호출할 수 있습니다. 인용문·코드·이메일 주소·외부 자료에 등장하는 이름은 실행 지시로 취급하지 않습니다. 실제 도구 호출은 연결된 에이전트가 수행합니다.

| MCP 도구 | 사용 방법 |
|---|---|
| `run_workflow` | `handle`, `task`로 시작합니다. 새 FLOW 워크플로우 실행에는 고유 `request_id`를 주고, 불확실한 응답을 재시도할 때 같은 ID와 내용을 재사용합니다. |
| `get_workflow` | 시작 때 받은 `run_id`, `run_kind`로 저장된 상태와 결과를 조회합니다. 재접속해도 새 실행을 만들 필요가 없습니다. |
| `list_workflow_runs` | 재접속 후 실행 ID를 잃었을 때 현재 범위의 실행 목록을 읽습니다. `limit` 기본 50/최대 200, 선택적인 `status` 필터를 사용합니다. |
| `wait_workflow` | 같은 실행을 기본 30초, 최대 60초씩 관찰합니다. `terminal=false`이고 `requires_decision=false`이면 반복합니다. |
| `decide_workflow` | 필요한 사람의 결정을 받은 뒤 워크플로우 승인을 전달합니다. 팀 예산 승인은 Arkism 앱에서 처리합니다. |
| `cancel_workflow` | 사용자가 요청한 새 `@워크플로우` FLOW 실행의 중단을 요청합니다. 이후 같은 실행을 조회해 실제 종료를 확인합니다. |

대기 시간이 끝났다는 것은 실행 완료나 취소가 아닙니다. 에이전트는 `terminal=true`가 될 때까지 같은 실행을 따라가고, 최종 `status`와 `result`를 사용자에게 전달해야 합니다. `requires_decision=true`이면 필요한 결정을 알리고 기다립니다. 재실행으로 대기를 대신하지 않습니다.

재접속 목록은 ID·작업 ID·상태·작업 종류·부모 ID·생성 시각·결과 조회 가능 여부만 제공합니다. 입력·프롬프트·정의·결과 본문은 포함하지 않습니다. `result_available=true`는 종료 상태의 결과를 따로 조회할 수 있다는 뜻이며 성공·품질·전달 완료나 비어 있지 않은 보고서를 보장하지 않습니다. 사용자의 현재 작업과 관련된 실행을 선택한 뒤 그 `id`를 `run_id`로, `run_kind=workflow`로 조회·대기를 이어갑니다. 목록의 모든 결과를 자동으로 대화에 넣거나 다시 실행하지 않습니다. 기존 assist·독립 meeting 기록은 이 목록에 포함하지 않습니다.

`run_kind`는 `workflow`, `assist`, `meeting`을 구별합니다. 기존 전문가·팀 실행은 시작 중복 방지를 지원하지 않는 경로가 있으므로 `idempotency_supported`를 확인하고 응답 불명 상태에서 무조건 다시 시작하지 않습니다. `cancel_workflow`는 기존 assist·meeting·`$워크플로우` 실행을 지원하지 않습니다. `cancel_requested=true`만으로 중단됐다고 표시하지 않으며 실제 종료 결과를 확인합니다.

### 앱과 채널의 지원 범위

| 경로 | 현재 범위 |
|---|---|
| 활성 MCP 대화 | 시작·조회·반복 대기·지원되는 승인/취소와 최종 결과 조회 |
| 에이전트 앱의 네이티브 `@` 선택창 | Arkism 작업을 앱 자체 선택창에 등록하는 기능은 미지원 |
| 닫히거나 비활성인 에이전트 대화 | MCP만으로 대화를 깨워 최종 메시지를 보내는 push는 미지원. 다시 연결해 기존 실행을 조회해야 함 |
| Discord | 저장된 호출 원점과 전달 기록으로 결과를 후속 전송하는 워커 구현. 아래 복구 경계 적용 |
| 다른 메신저 | 후속 구현 대상. 기존 발신 알림 기능을 대화형 FLOW 호출·최종 전달 지원으로 간주하지 않음 |

이 코드의 로컬 검증과 실제 앱별 실행·운영 Discord 송신 검증은 별도입니다. 앱을 닫은 뒤 자동으로 결과가 도착하는 요구 전체를 MCP 지원만으로 충족했다고 표시하지 않습니다.

## Discord 결과 전달과 복구

새 FLOW 호출은 요청 이벤트의 ID와 호출 원점(봇·서버·채널·스레드·사용자)을 실행에 연결합니다. 같은 요청의 재접수는 새 실행을 만들지 않으며, 결과 전달 기록을 서버의 영속 작업으로 보관합니다. 봇 재시작 후에는 이 기록을 읽어 후속 전달을 이어갑니다. 구 서버의 로컬 추적 폴백은 같은 내구성 보장을 제공하지 않습니다.

승인이 필요하면 같은 대화에 실행 ID와 FLOW 앱 안내를 보냅니다. 일반 승인은 앱에서 처리하고, 기존 예산 승인 버튼은 유지합니다. 대기 실행도 서버 기록에서 다시 찾으므로 봇 재시작 뒤 안내를 이어갈 수 있습니다.

최종 보고서는 Discord 길이 제한에 맞게 나눠 보내며, 각 부분의 메시지 ID를 영수증으로 저장합니다. 결과 revision과 본문 해시를 고정하므로 재접속 후 다른 결과나 다른 분할 방식으로 이어 보내지 않습니다. 이미 확인된 부분은 보존하고, 각 부분을 보내기 전에 현재 채널·사용자·봇 권한을 다시 확인합니다.

| 전달 상태 | 의미와 처리 |
|---|---|
| `waiting_run` | 실행의 종료를 기다림 |
| `pending`, `sending` | 보내기 전 또는 한 부분의 전송을 처리 중 |
| `retry_wait` | 명시적으로 재시도 가능한 실패 뒤 대기 |
| `unknown` | 실제 전송 여부를 확정하지 못함. 자동 재전송하지 않음 |
| `failed` | 권한 등 확인된 실패. 원인을 해결한 뒤 상태를 검토해야 함 |
| `delivered` | 서비스가 반환한 메시지 ID를 모두 확인함. 사람이 읽었다는 뜻은 아님 |

전송 응답 유실이나 전송 중 lease 만료는 `unknown`으로 남깁니다. 먼저 해당 Discord 스레드와 부분별 영수증을 확인해야 하며, 결과를 다시 보내기 위해 조사를 다시 실행하지 않습니다. 외부 메시지 시스템에서 정확히 한 번 도착함을 보장하는 기능으로 표시하지 않습니다.

## 결과의 보존과 한계

MCP와 Discord는 저장된 실행 정의와 종료 노드의 결과에서 같은 보고서를 구성합니다. 짧은 상태 요약만으로 긴 조사 결과를 대체하지 않습니다. 구조화된 보고서의 제목·요약·본문 구간·표·번호와 링크가 있는 출처·확인하지 못한 점·한계·검토 결과를 전달합니다. 실행이 실패하거나 중단됐으면 완료된 다른 가지의 출력으로 전체 성공을 표시하지 않습니다.

연구 보고서는 저장되는 노드 출력 전체의 20,000자 한도를 검사합니다. 한도를 넘으면 출처나 본문을 잘라 성공으로 저장하지 않고 실패를 반환합니다. 이 한도에는 출력의 JSON 포장도 포함됩니다. 보고서를 한도 안에서 다시 작성하는 것과 이미 잘린 결과를 완전하다고 표시하는 것은 구별합니다.

기본 조사 템플릿의 제한된 읽기·검색 실행은 현재 확인된 Claude CLI 어댑터만 지원합니다. 필요한 로컬 CLI 옵션이 없거나 지원하지 않는 실행기를 선택하면 조사를 했다고 주장하지 않고 오류를 반환합니다. 기존 다중 모델 리서치의 모델·예산·스킬을 이 템플릿에 맞춰 자동 변경하지 않습니다. 기존 모든 `read` 단계가 이 전용 어댑터와 동일한 도구 제한을 가진다는 뜻도 아닙니다.

API 필드는 [OpenAPI 명세](../api/openapi.yaml), 이번 변경의 검증 범위는 [작업 기록](work-records/2026-10-28-flow-research-integration.md)을 참고하세요.
