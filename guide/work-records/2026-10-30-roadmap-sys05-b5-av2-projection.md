# project a real dynamics run onto the unchanged A-v2 summary

Task: SYS-05.B (#152)
Research: Engineering measurement with a synthetic in-process plan on an own disposable PostgreSQL; a development run, not a locked comparison, performance claim or tail estimate.
Design: The A tools stay unchanged. A Go PG test generates the A workload from an sys05-load-config-v1 config (2 s, two updates, a read, an update, a read, and one repair_block fault at 700 ms), runs each request against the real dynamics queue in async and sync mode, and writes a raw run (sys05-b5-raw-run-v1) with absolute times and the config and workload hashes. A new adapter, measurement_adapter.py, moves every time to the run anchor and writes the A-v2 ledger and observations; the unchanged summarize_load.py then checks them. The adapter keeps unknown values null and never invents a stage: an update keeps only the observed prefix of admission, durable, applied and visible, stopping at the first missing witness; background operations are refused, and a read's read_at is its completion (an upper bound, so the age stays conservative). A snapshot time is recorded only when the snapshot generation is the same before and after the read; quality passes only for a selected read whose result contains the target exactly when it is not deleted. The repair interval comes from the server-side LastRepairStartNS and LastRepairEndNS and the publication time. It is reported only when the harness itself read the hold with the same origin before the repair, and the adapter refuses a hold witness outside the interval. The validation hash is the server's commitment to the republished snapshot, recomputed by the test from the served copy. The fault runs at its planned 700 ms. Costs are sampled twice, just before the fault and at the end, because the purge after the delete scrubs stored receipts; each sample fills all nine A cost fields, with receipt and replay as raw stored slices.
Relation: adapted
Deviation: The raw run is produced by an in-process test, not by a separate service process, so service_execution_authenticated stays false. Background coverage (privacy, embedding) is reported as unknown.
Why: The card needs the B measurement to feed the same A-v2 summary as the comparison side, without changing the locked A contract, its schema or expected values.
Verified: Own disposable PostgreSQL, under plain and -race. Async: reconciliation complete, comparison_input_ready true, v2_repair_coverage_ready true, one repair interval of 130 ms from the delete race to the republish. All nine costs were known in both samples of both modes; before the fault the stored receipt slices were 3956 bytes in async and 4545 in sync, and the replay slices 1455 in each; after the purge both are 0. Sync: reconciliation complete; nothing was withheld, so no interval was reported and both readiness values are false, as the summarizer requires. Altered copies of each real run were refused with the intended error code: a dropped ingress line, a duplicated ingress line, an admission one nanosecond before its receipt, a read relabeled as an update and a swapped config hash, and in async a hold witness before the origin or after the republish. An independent code review found that coverage was built from one value, the validation hash was unchecked, readiness was not asserted, the fault ran late and refusals did not check their code; all five were fixed, and the run was repeated. Python: 45 tests in the sys_05 folder passed, including a new adapter test with no database. A failed quality value removed comparison_input_ready, and dropping the async repair removed v2_repair_coverage_ready. golangci-lint v2.14.0: 0 issues. The complexity tool added no function above its limit. The unchanged A compare on the two projected runs reports same_common_inputs true and comparison_ready false, and the test asserts exactly that: sync serves its previous snapshot during a purge, so it has no repair interval and its v2 coverage stays incomplete. An attempt that reported the sync publish hold as a repair interval and fixed both windows at the planned end did turn comparison_ready true; an independent review rejected it, because a held publish is not a serving outage and the equal elapsed time came from the fixed end, so it was reverted.
Limits: Not accepted. The cost fields are logical slices and process or database sizes from one process: receipt and replay overlap ledger and state bytes and are not additive, and rss_bytes is the shared test process. The interval origin is still server-recorded: the harness confirms the hold and its origin, but does not watch continuously from the origin, so coverage relies on that record. validated_ns is the server's repair end. Read and update stage times are upper bounds (enqueued equals accepted; a read is accepted at its completion), so some order checks hold by construction. The 1300 ms read uses a snapshot about 0.7 s old against a 1 s freshness limit, so a slow host may fail it. N=1 per mode on a 2 s plan with five requests; the queue samples are taken after drains, so the reported backlog depth is always 0 and says nothing about queueing under load. Fixed sleeps set the plan; a slow host shifts request times but the summarizer still checks the order. No separate-process service run, and no ready same-condition comparison or nine-cost comparison: under the current v2 rules sync cannot become comparison-ready, which is a result, not a gap to fill with a synthetic interval. The plain and race runs share one result folder, so the kept report is the race run. Full check_local and unrestricted go test ./... were not run.

## 한국어 작업 기록

제목: 실제 동적 대기열 실행을 바꾸지 않은 A-v2 요약기에 투영
이유: 카드는 B 측정이 비교 대상과 같은 A-v2 요약을 거치도록 요구한다. 잠근 A 계약·스키마·기대값은 바꿀 수 없다. 그래서 Go 시험이 A 생성기의 요청열을 실제 대기열에 돌려 원시 기록을 남기고, 새 adapter가 그 기록을 A-v2 형식으로 옮긴 뒤 원래 요약기가 검사한다.
검증: 자체 임시 PG에서 일반·race 모두 통과했다.
- 비동기: 대사 완결, comparison_input_ready true, v2_repair_coverage_ready true, repair 구간 1건(삭제 경쟁부터 재게시까지 130 ms). 시험이 repair 전에 보류와 그 원점을 직접 읽었고, 검증 해시는 공개된 스냅숏에서 다시 계산해 맞췄다.
- 동기: 대사 완결. 보류가 없어 구간이 없고, 요약기 규칙대로 두 준비 값은 false다.
- 대조: 실제 실행을 바꾼 사본은 의도한 오류 코드로 거절됐다(ingress 한 줄 삭제, ingress 중복, 수신 1 ns 전 접수, read를 update로 바꿈, config 해시 교체, 비동기에서 보류 확인 시각이 원점 앞이거나 재게시 뒤). quality를 실패로 바꾸면 comparison_input_ready가 사라지고, 비동기 repair를 지우면 v2_repair_coverage_ready가 사라졌다.
- 독립 코드 검토의 지적 5건(구간을 한 값으로 만듦, 검증 해시 미확인, 준비 값 미단언, fault 지연, 거부 코드 미확인)을 모두 고치고 다시 돌렸다. Python 시험 45건 통과(DB 없는 adapter 시험 포함).
- 9비용: 장애 직전과 끝에 두 번 쟀고, 두 방식 모두 아홉 값이 다 측정됐다. 삭제 뒤 purge가 저장된 receipt를 지우기 때문에 장애 직전에 쟀다. 그때 receipt 조각은 비동기 3956·동기 4545 바이트, replay는 둘 다 1455 바이트였고, purge 뒤에는 둘 다 0이다.
- lint 0건, 복잡도 한도를 넘는 함수 추가 없음.
- 같은 조건 비교: 원래 A compare에 두 실행을 넣으면 공통 입력은 같고 comparison_ready는 false다. 시험이 이 값을 그대로 단언한다. 동기 방식은 purge 중에도 이전 스냅숏을 서빙하므로 repair 구간이 없고 v2 범위가 incomplete로 남는다. 동기의 게시 보류를 구간으로 보고하고 두 실행의 끝을 계획 시각에 고정하면 true가 나왔지만, 독립 검토가 '게시 보류는 서빙 중단이 아니고 같은 경과 시간은 고정 때문'이라고 반려해 되돌렸다.
한계: 미수용 상태다. 비용 값은 한 프로세스 안에서 잰 논리 조각과 프로세스·DB 크기다. receipt·replay는 ledger·state와 겹쳐 더할 수 없고, rss_bytes는 시험 프로세스 전체 값이다. 구간 원점은 여전히 서버 기록이다. 시험은 보류와 원점을 확인하지만 원점부터 계속 지켜보지는 않는다. validated_ns는 서버의 repair 종료 시각이다. 단계 시각은 상한값이라(enqueued=accepted, read는 완료 시각에 접수) 일부 순서 검사는 저절로 통과한다. 1300 ms 읽기의 스냅숏 나이가 약 0.7초(한도 1초)라 느린 호스트에서는 실패할 수 있다. 모드마다 1회, 2초·요청 5건짜리 개발 실행이다. 대기열 표본을 drain 뒤에 찍어서 backlog 깊이는 늘 0이고, 부하 아래 대기열에 대해서는 아무것도 말하지 않는다. 같은 프로세스 안 시험이라 service_execution_authenticated는 false다. 프로세스를 나눈 실제 실행은 아직 없다. 지금 v2 규칙에서는 동기가 비교 준비 상태가 될 수 없어 준비된 같은 조건 비교와 9개 비용 비교도 없다. 이는 결과이며, 합성 구간으로 메울 빈칸이 아니다. 일반·race가 같은 결과 폴더를 써서 남은 보고서는 race 실행 값이다. 전체 check_local과 무제한 go test는 실행하지 않았다.
