# Finish the queue's publication within the existing worker-round budget

Task: SYS-05.B (#152), PR #552 CI follow-up
Research: none
Why: The full-queue crash test stopped launching worker rounds as soon as the queue count reached zero. Applying an entry and publishing the resulting snapshot are separate transactions inside one bounded worker substep. The final apply can commit before that substep expires while publication remains outstanding. CI reported four completed entries, an empty queue, no hold, and publication generation zero; the test had stopped after three of its four allowed rounds. Its plain dependency_unavailable strings did not preserve the underlying error, so the exact CI dependency failure cannot be reconstructed from that log alone.
Changed: The test now uses the original maximum of four rounds until an error-free round observes an empty queue and advances the publication generation relative to that round's starting value. Exhausting the budget fails explicitly; an older prefix publication or a publication no-op cannot satisfy completion. Child reports preserve whether the configured one-second worker deadline actually expired. Only deadline errors, or dependency-unavailable errors accompanied by that deadline evidence, may continue to another already-budgeted round; unexpected failures stop immediately. Test-only injection commits a real apply transaction and then waits for that unchanged deadline. Separate cases cover no previous publication and a previous prefix publication. The child environment is a fixed allowlist, so injection settings do not leak into ordinary workers. No production worker behavior, lease, wait limit, retry count or CI retry policy changed.
Verified: On disposable PostgreSQL 18 with Go 1.27.4 and GOMAXPROCS=2, the old queue-count exit condition failed deterministically after two injected deadlines: head=4, count=0, four done entries, one native event, no hold, publication generation=0. With the corrected completion condition, the batch-deadline case completed in three rounds (deadline, deadline, ok), advancing publication from zero to one. The final-batch-only case completed in three rounds (ok, deadline, ok), advancing the earlier prefix publication from generation one to two. The final race run passed three top-level tests and seven subtests in 37.642 seconds with no failures or skips, including the existing live-lease, late-drain, killed-apply and full-queue cases. Windows-targeted go vet, the repository cyclomatic-complexity gate, and the cached gocognit checker with threshold 20 passed. The owned test databases were removed successfully.
Limits: This demonstrates a real committed-apply/deadline boundary and fixes the test's premature completion criterion. It does not prove that every unavailable response in the historical CI run had that cause. The same CI job's CodeGraph timing failure remains separate: local original-test comparisons passed on PostgreSQL 18 (39.095 ms impact query) and PostgreSQL 16 (50.544 ms), with the same 2,020-file, 24,125-symbol, 67,836-edge graph; neither establishes the cause of the CI slowdown. CodeGraph's existing isolated retry did not report success, and its old failure output was not retained. No CodeGraph product changes, relaxed thresholds, new retries, model calls or release build were introduced here. Full CI must run again.

## 한국어 기록

대기열 항목 적용이 끝나도 검색에 쓸 결과 게시가 남을 수 있었다. 기존 테스트는 대기열이 비었다는 이유만으로 다음 작업자 실행을 중단했다. 실제 PostgreSQL에서 마지막 적용은 커밋하고 기존 1초 제한을 넘기도록 주입해, 항목 4개 완료·대기열 0·게시 0 상태를 재현했다.

이제 원래 허용된 최대 4회 안에서 마지막 작업이 오류 없이 끝나고 새 게시 세대가 생겨야 완료다. 이전 일부 항목의 게시만 남은 경우도 별도로 검증했다. 두 주입 사례 모두 3회 안에 게시까지 끝났고, 기존 crash 검사까지 3개·하위 7개가 race 검사로 통과했다. 제한시간이나 재시도 횟수는 늘리지 않았으며, 과거 CI의 정확한 하위 오류 원인과 CodeGraph 지연 원인은 확인되지 않았다고 구분해 기록한다.
