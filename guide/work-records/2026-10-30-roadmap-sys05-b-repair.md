# verify-then-republish a withheld dynamics queue

Task: SYS-05.B (#152)
Research: Engineering measurement with a synthetic in-process plan on an own disposable PostgreSQL; a development run, not a locked comparison, performance claim or tail estimate.
Design: A failed queued entry already withheld publication, admission and claims, but nothing could release the hold, and RepairStartNS was read but never set. The worker now records the repair origin when it first withholds (an older marker without origin stays null). The new explicit RepairDynamicsPublication needs the same service write:jobs authority as Publish. It refuses a live lease and, through the shared publication checks, a pending purge. It clears an expired lease so its claim stays fenced, records the interval as LastRepairStartNS and LastRepairEndNS (absolute times, so a later window projection can use them), refuses a restore or a pending purge even when there is nothing to republish yet, and rebuilds the snapshot from canonical rows in the same transaction. With queued work, only the applied prefix is published, as in Publish. With no applied prefix yet, only the hold is released. The condition run now purges, repairs and searches again after the delete race.
Relation: adapted
Deviation: A drained queue is not required, because the worker refuses to claim while withheld and such a rule would strand queued work. The publication interval is skipped only for this explicit repair. The receipt and replay slices are now read before the purge, which scrubs stored receipts.
Why: The card asks to block serving during repair and republish after verification, recording the queue delay and the serving-outage cost. Before this change a withheld queue, or an expired lease under a hold, could never recover.
Verified: Own disposable PostgreSQL. Async: the delete race withheld, eight purge steps ran, the repair closed an interval of 293 ms, republished, and the next search selected the snapshot without the deleted memory. The outage from the delete to the republish was 445 ms. Sync withheld nothing (the repair answered conflict), and after the purge the normal publish resumed with an outage of 277 ms. These values come from the kept report of the final run, written by the -race pass; an earlier plain run before the review fixes measured 201 ms inside 297 ms, and 148 ms for sync. TestDynamicsLoadRepairRepublishPG covers several refusals and recoveries. A live lease is refused. A worker cannot claim while the queue is withheld. A read-only principal is denied and writes nothing. The repair clears an expired lease, and the old claim is then rejected. Queued work resumes and applies. An unknown origin closes with no interval, and a second repair is a conflict. Nine altered copies of each condition run that touch the repair were refused, including a repair interval longer than the outage, an altered repair result and a left-over origin; three of these were added after an independent code review. Six source mutations each failed a test: keeping the hold, allowing a live lease, dropping the interval, dropping the origin, skipping the republish and keeping the lease token. The last mutation first survived and was killed after a lease assertion was added. The mutations ran before the review fixes and were not rerun after them. TestDynamics and TestWorkOnceAdvancesPrivacy in internal/memory: 270 passed, 1 pre-existing skip, under plain and -race. golangci-lint v2.14.0: 0 issues. The complexity tool added no function above its limit.
Limits: Not accepted. A snapshot over its size or item limit makes the repair roll back, so the hold then stays until the limits or the data change; the queue does not move meanwhile. No test reaches the release-only path with a pending purge. N=1 per cell. Durations come from development runs, and the race-mode run is slower. The outage is measured by the test harness, while the repair interval is server-side, and in this run the interval sits inside the outage. The repair is an explicit call: no daemon schedule or HTTP route invokes it yet. Sync has no repair interval, because nothing was withheld there. A-v2 comparison_ready stays false, and SYS-05 stays in_progress pending independent acceptance. Full check_local and unrestricted go test ./... were not run.

## 한국어 작업 기록

제목: 보류된 동적 대기열을 검증한 뒤 다시 게시
이유: 카드는 repair 중에는 제공을 막고, 검증한 뒤 다시 게시하며, 대기 지연과 제공 중단 비용을 기록하라고 요구한다. 지금까지는 실패한 항목이 게시를 보류시키면 그 보류를 풀 길이 없었고, repair 시작 시각은 읽기만 하고 기록하지 않았다. 이제 repair 구간을 시작·끝 절대 시각(LastRepairStartNS, LastRepairEndNS)으로 남기고, 다시 게시할 것이 아직 없어도 복원 중이거나 purge가 남아 있으면 보류를 풀지 않는다. 그래서 보류된 대기열, 또는 보류 중 만료된 lease가 있는 대기열은 다시 살아나지 못했다.
검증: 자체 임시 PG에서 실행했다.
- 비동기: 삭제 경쟁으로 보류가 걸렸다. purge 8단계를 처리한 뒤 repair가 293 ms 구간을 닫고 다시 게시했다. 그다음 검색은 지운 기억 없이 스냅숏을 사용했다. 삭제부터 재게시까지 제공 중단은 445 ms였다. 이 값은 마지막 실행의 race 모드 보고서 값이고, 검토 반영 전 일반 실행은 297 ms 중 201 ms, 동기 148 ms였다.
- 동기: 보류가 없어 repair는 conflict를 돌려줬다. purge 뒤 정상 게시가 이어졌고, 중단은 277 ms였다.
- 단위 시험: 살아 있는 lease 중에는 repair를 거부한다. 보류 중에는 worker가 claim하지 못한다. 읽기 전용 주체는 거부되고 아무것도 쓰지 않는다. 만료된 lease는 repair가 걷어내고, 옛 claim은 거절된다. 대기 작업은 재개되어 적용된다. 원점을 모르는 보류는 구간 없이 닫히고, 두 번째 repair는 conflict다.
- 대조와 변이: 실행 결과를 바꾼 repair 사본 9종을 모두 거절했다(구간이 중단보다 긴 경우, repair 결과 변조, 원점 잔존 3종은 독립 코드 검토 뒤 추가). 코드 변이 6종(보류 유지, 살아 있는 lease 허용, 구간 누락, 원점 누락, 재게시 생략, lease 토큰 유지)도 모두 실패로 잡혔다. 마지막 변이는 처음에 살아남아서 lease 단언을 추가해 잡았다. 변이 시험은 검토 반영 전에 돌렸고, 반영 뒤에는 다시 돌리지 않았다.
- 일반 실행과 race 실행 모두 270건 통과했다(기존 skip 1건). lint는 0건이고, 복잡도 한도를 넘는 함수는 추가되지 않았다.
한계: 미수용 상태다. 스냅숏이 크기·항목 한도를 넘으면 repair가 롤백되어 보류가 풀리지 않고, 그동안 대기열도 멈춘다. 게시할 것 없이 보류만 푸는 경로에서 purge가 남은 경우는 시험이 닿지 않는다. 칸마다 1회만 실행한 개발 실행이다. 중단 시간은 시험 쪽에서 쟀고, repair 구간은 서버 쪽 값이다. repair는 명시적으로 호출해야 하며, 데몬 일정이나 HTTP 경로는 아직 없다. 동기는 보류가 없어 repair 구간이 없다. A-v2 comparison_ready는 false이고, SYS-05는 독립 수용 전까지 진행 중이다. 전체 check_local과 무제한 go test는 실행하지 않았다.
