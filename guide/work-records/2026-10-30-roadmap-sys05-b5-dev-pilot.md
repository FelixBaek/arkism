# run a same-plan sync/async development pilot with ledgers and costs

Task: SYS-05.B (#152)
Research: Development pilot of the B5 measurement design with synthetic fixtures in an isolated database; no locked comparison, performance, quality or scientific claim.
Design: One new test file reuses the native search fixture, the genuine LOGIN connection and the real Handler behind a loopback server. An ingress wrapper records the exact body hash and arrival time before the Service is called; client sends and responses are a separate ledger; a serial readback that finds the evaluation, capture and queue entry supplies the durable witness, and the done entry with a native receipt the applied witness; a serial Search that added exactly one observation with status selected supplies the visible witness. The same plan (five updates, a replay, a conflicting retry, one Search) runs once in async and once in sync mode. A cost channel reads only the own test database and this process.
Relation: adapted
Deviation: The design's separate observer file, Python A-v2 adapter, protocol file and Root pilot lock were not produced. The five updates share one trace with distinct EventIDs, so they count as one learning plus duplicates, not five independent updates. Sync mode required adding read:jobs and write:jobs to the caller; this is recorded in the report.
Why: The design required checking that ingress, request and canonical readback ledgers and the nine cost dimensions can actually be collected for both modes before any locked comparison.
Verified: Against an own disposable PostgreSQL: async admitted four updates, refused the fifth with dynamics_queue_full, then drained; sync applied all five in-request with the same witness for durable and applied; in both modes the replay returned the original evaluation, the changed retry returned 409, exactly one receipt consumed learning, and the Search observed status selected after publication. Ten altered copies of each real run (missing or extra ingress, ingress outside its request window, double-counted retry, updates dropped together, overload hidden as another failure, conflict as success, duplicate as learning, baseline as native, applied before durable) were refused. Disabling the learning-count check made the duplicate-as-learning control fail the test. An independent read-only review found no fabricated or dropped data and six weaker points (search binding, durable witness scope, plan denominator, backend RSS process check, untested branches, two cost labels); all were fixed. After the fixes TestDynamicsMeasurementPilotSyncAsyncPG passed 3/3 and under -race 3/3. golangci-lint v2.14.0 reported 0 issues. The disposable database was stopped with no leftover test databases or roles.
Limits: Not a comparison: N=1 per cell, one in-process run, no restart, burst, sustained overload, cold/warm, delete race or repair window, no A-v2 projection, comparison_ready stays false. receipt_bytes and replay_bytes are null; RSS is one shared test process (async runs first, so sync carries order bias) plus DB backends with shared pages. No body-hash mismatch, null-as-zero or budget-overrun control exists yet. Witness times are bounded by the serial readback cadence, not commit instants. Full check_local and unrestricted go test ./... were not run. SYS-05 stays in_progress; 25/63 done, 24 required remaining.

이유: 잠근 비교를 하기 전에, 두 방식 모두에서 수신·요청·정본 읽기 원장과 9가지 비용을 실제로 모을 수 있는지 설계대로 확인해야 했다.
