## 검증 기준

- 코드가 존재하는 것과 실제 기능이 동작하는 것을 구분한다. 실제 Capture/승인/Search/BuildContext/worker/API/UI 경계를 통과하는 시험을 각 항목에 연결한다.
- 버그 후보는 수정 전 실패와 수정 후 성공을 기록한다. 정책 변경은 기존 정책을 보존한 명시적 옵션과 비교 검증을 포함한다.
- 범위·권한·삭제·격리·원본 revision 검증, frozen context 및 외부 전송 경계를 유지한다.
- Go 검사는 메모리 패키지로 제한하고 `systemd-run --user --scope -q -p MemoryMax=6G timeout 900 go test ./internal/memory`로 실행한다. 관련 기능시험 후 통합 패키지를 확인한다.
- UI는 관련 로컬 시험, 로컬 코드 검사, 실제 화면·키보드 확인을 별도로 기록한다.
- 고정 오프라인 검색 평가는 기존 하네스·잠금·입력·예산을 유지한다. 모델 호출 감지 결과와 모든 분류의 행별 차이를 확인한다.
- 제품 빌드·운영 배포·원격 push는 이번 작업에 포함하지 않는다. 필요한 테스트 실행 파일과 승인된 오프라인 하네스만 사용한다.

## 전 영역 추가 점검 범위

1. 수집·입력 검증·파일 및 세션 가져오기·출처·승인·수정·중복·만료
2. 엔티티·관계·관찰·반영·요약·지식 파생과 작업 복구
3. 검색·순위·시간·그래프·임베딩·다국어·문맥 예산과 실제 전달
4. 피드백·평가·신호·동적 상태·UI·호스트/도구/SDK 연결
5. 저장소·이관·백업/복원·개인정보 삭제·권한/범위·외부 전송
6. 작업 큐·임대/재시도·보존 정리·관측/진단·확장 연결과 운영 경계

각 점검 기록은 본 파일과 별도의 근거 보고서에 조사 파일·기존 시험·확인된 동작·개선 가설·미실행 검증을 구분한다. 파일 목록만 확인한 것을 상세 검토 완료로 표시하지 않는다.

## 현재 검증

구현 착수 시 기준 브랜치가 깨끗하고 세 구현 작업 트리가 같은 기준 커밋에서 분리됨을 확인했다. 새 구현 시험·통합 시험·추가 품질 측정은 아직 완료되지 않았다.
