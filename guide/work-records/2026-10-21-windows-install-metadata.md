# 2026-10-21 Windows 설치 등록·바로가기 복구

작업 ID: Task: none (공개 평가 P1-7, 폴더 교체와 설치 메타데이터의 일관성)

## 이유와 변경

폴더만 되돌려도 새 버전의 바로가기·제거 등록이 남으면 설치 복구가 끝난 것이
아니다. 앞선 Windows 교체 코어의 Metadata 인터페이스에 실제 Windows 구현을
연결했다. 제품 NSIS와 helper 패키징은 아직 연결하지 않았다.

공개 factory는 현재 사용자 SID, HKCU의 Arkism 제거 등록, Windows가 알려 주는
시작 메뉴·바탕 화면의 Arkism.lnk만 사용한다. 임의 레지스트리 키나 링크 경로를
외부 옵션으로 받지 않는다. 기존 설치는 같은 설치 위치의 제거 등록과 알려진
프로그램 파일로 확인한다. 다른 설치나 등록되지 않은 비어 있지 않은 폴더는
채택하지 않는다. 처음 지정한 빈 폴더는 설치와 실패 복원을 지원한다.

기존 레지스트리 값의 형식·바이트와 바로가기 원본을 checkpoint에 저장한다.
현재 값이 원래 값 또는 이 설치가 쓴 값인지 확인하고 Windows KTM 트랜잭션으로
등록을 적용·원복한다. 알 수 없는 기존 값은 보존한다. 그 뒤 생긴 값·하위 키나
다른 내용은 추측해 지우지 않는다.

바로가기는 Windows COM으로 메모리에서 만들고, 고정 경로와 이동 추적 금지를
확인한다. 읽기 과정은 Resolve를 호출하지 않는다. 파일은 쓰기·삭제 공유를 막는
핸들로 확인하고, 같은 핸들로 원본을 임시 보관한 뒤 새 파일을 rename한다.
대상 파일이 중간에 생기면 덮어쓰지 않는다. 실패 시 원본 파일을 그대로 되돌린다.
임시 파일 이름은 checkpoint의 무작위 ID와 고정 경로에서만 만든다. 쓰다 중단된
새 파일은 기대 바이트의 prefix인 경우에만 정리한다. 다른 내용은 보존한다.

Metadata.Commit은 선택적 duck typing 대신 필수 계약이다. 완료 기록을 남긴 뒤
보관한 링크를 정리한다. 이 단계가 실패해도 완료한 payload를 원복하지 않는다.
다음 실행이 정리를 재시도하며, 완료 후 사용자가 바꾼 현재 링크는 건드리지 않는다.
재시도하는 설치의 버전 입력이 달라도 checkpoint가 기록한 대상 버전으로 판단한다.
검사는 같은 구현의 0.3.0 입력으로 0.2.0 이력을 복원했다. 초기 빈 설치 폴더의
원복도 별도로 검증했다.

## 실행한 검증

- 실제 Windows Go 도구로 전체 패키지 검사 통과. 하위 사례 97개, 문장 커버리지
  78.7%. 새 설치/업그레이드의 실제 metadata 중단 14개와 기존 payload 중단
  12개를 합쳐 실제 자식 프로세스 종료 후 복구 26개가 통과했다. defer 없는 종료
  코드 77을 사용했고 전원 장애 검사는 아니다.
- 실제 KTM registry와 Windows 파일 핸들·COM을 사용했다. 실제 사용자 제거 키나
  바탕 화면 대신 새 소유 registry namespace와 테스트 폴더만 사용했다.
  등록 값 쓰기 중 프로세스가 끝나도 일부 값이 공개되지 않았다.
- 레지스트리 적용 직후와 각 링크의 원본 이동/새 파일 공개 직후를 중단했다.
  이전 파일·바로가기·등록을 함께 복원했고 완료 기록 후에는 새 설치를 유지했다.
  완료 정리 실패도 새 설치를 원복하지 않고 수리 후 재시도했다.
- 실제 폴더를 이동한 뒤 새 파일로 교체했다. Windows Script Host가 같은 링크를
  읽었고, 일반 Windows Resolve도 이전 폴더를 따라가지 않고 현재 경로를 골랐다.
  공개된 새 링크가 숨김 상태가 아닌 것도 확인했다.
- 다른 설치·사용자 변경·동시 파일 생성·외부 registry 값·손상된 checkpoint와
  경로 재지정을 거부했다. 정상 prefix의 불완전 임시 파일은 지우고, 다른 내용은
  그대로 남겼다. 설정된 디렉터리의 링크는 먼저 실제 위치로 확인하고, 변경 작업의
  경로에서 나중에 발견한 namespace 재지정은 거부했다.
- 실행 후 소유 registry namespace 48개가 모두 없어졌고, 테스트 프로세스와 최종
  임시 폴더 잔여는 0개였다. 실제 제품 앱·DB·설치/제거는 실행하지 않았다.
- Windows GOOS vet·테스트 바이너리 컴파일, 복잡도 검사, actionlint, diff 검사,
  Codecov YAML 로컬 파싱 통과. 패키지 함수/closure 125개의 최대 순환 복잡도 19,
  기존 부채 381개에 증가 없음. 다른 OS 앱 빌드는 실행하지 않았다.

## 실패와 보강

Windows COM에서 ID list를 비우거나 이동 추적 플래그를 경로 설정보다 먼저
적용하면 저장된 경로가 없어지는 것을 실제 검사에서 발견했다. 먼저 경로를
설정하고 필요한 플래그를 보존해 추적만 끄도록 고친 뒤 Windows가 다시 읽고
해석하는 검사를 통과했다. 반환 포인터 변환의 vet 경고는 out-pointer를 받는
스트림 API로 바꿔 해결했다. 검사 launcher의 PowerShell 인자 인용도 수정했다.

확장한 validator와 복구 함수가 복잡도 게이트에 거부돼 검증·완료 복구 단계로
분리했다. 기준선이나 80% patch 목표를 낮추지 않았다. 최종 소스 전체를 다시
Windows에서 빌드·검사했다.

정리 근거를 수집할 때 PowerShell JSON 배열이 한 항목으로 감싸진 것을 실제
항목 수 대조에서 발견했다. 문자열 배열로 변환하고 경로 48개를 각각 검사한
결과로 근거를 갱신했다. launcher나 수집기 성공만으로 정리를 통과시키지 않았다.

## 커버리지 보고와 남은 작업

Windows 전용 Go 소스의 실행 근거가 Linux 보고서에서 빠지지 않도록 Checks의
native profile을 Codecov `go_windows`로 올리는 경로를 추가했다. 과거 수치는
carry forward하지 않는다. Linux Go·UI·Windows 세 업로드를 받은 뒤 상태와
댓글을 내도록 설정했다. 설정은 [Codecov 공식 문서](https://docs.codecov.com/docs/notifications)와
대조했고 로컬 YAML 파싱만 실행했다. 원격 업로드·80% patch 상태·전체 CI는
미실행이며 로컬 78.7%를 원격 게이트 통과로 표시하지 않는다.

제품 NSIS의 파일별 덮어쓰기·고정 Sleep은 아직 바꾸지 않았다. helper의 인증된
payload inventory, 생성된 제거 파일, 바로가기/등록 구현을 묶어 실제 설치 경로에
연결하고 최종 설치·업그레이드·제거를 disposable Windows에서 검증해야 한다.
실제 사용자 프로필, DB 마이그레이션, 전원 장애, OneDrive/네트워크의 실제 알려진
폴더, 서로 다른 버전의 helper 바이너리 사이 복구, 과거 버전 보존 개수 제한,
원격 실행·push·릴리스는 미실행이다.

커밋 상태: 검증한 Windows 구현·검사·보고 경로를 별도 로컬 커밋으로 기록.
기존 서명 설치 파일 변경과 외부 게시 없음.
