# Label-free source materialization through the original native engine

Task: EXP-02 (#153), consumed by EXP-03 (#153)
Research: Reproducible offline synthetic source-view engineering. No empirical outcome or scientific approval.
Design: A separate materializer consumes original PlanEvent rows, one current/historical QueryPlan, explicit synthetic admission/feature/qualification catalog, registry and fixed plan. It receives no gold or split labels. It validates the original observed prefix and emits candidate, event, feature, probe and manifest bundles. Existing authoritative Go DecodeStrict/CanonicalSHA256 hashes an allowlisted stream of projections; the explicitly pinned existing Go test executable provides the offline service during tests. Existing codecs and v1 DTOs are unchanged. Historical native time is the requested observed view; current withdrawal fences all revisions of the same logical identity, including withdrawals attached to a newer revision. A separate explicit v2 materialization mapping binds this time to the original query/gold; v1 retains its previous identity-clock behavior. Missing historical bodies are never replaced by current bodies. Admissions, importance, trust, context units and optional outcome qualification are explicitly synthetic fixture inputs; source visibility does not grant authority or independent qualification.
Relation: partial
Deviation: The original EXP02 plan/verify-index builder still reports external_contract_pending. This new source materializer is one required engineering component; it does not remove the remaining formal producer or simulate an owner acceptance. Late source outcomes on already invalidated native targets remain recorded and produce the original engine's invalidated_target failure. They are not silently removed, relabeled unknown or converted to successful empty predictions. Explicit qualification does not override the lifecycle fence.
Why: A real original-source-to-native producer was absent, preventing actual positive native REF selection and complete final-protocol E2E. Reusing authoritative Go hashing avoids implementing a divergent Python canonical encoder. Functional checks exposed a real cross-revision privacy fence gap and a missing inline EvidenceBinding schema lookup; both were fixed.
Verified: Source14 unit cases and projection26 cases pass. Actual Go/Python integration runs ten materialized source views through all seven original policies and original fresh verification: pending/current/historical revisions; unqualified and explicitly qualified stale outcomes; current withdrawal of old/new revisions while reading history; no admission; and unqualified/explicitly qualified live outcomes. Every bundle runs and replay-verifies. Eight views require successful predictions; two stale-outcome views require exactly four invalidated_target failures each, with no successful decision attached to failed rows. The ten views retain all70 scheduled predictions, including8 expected failures. The real materializer CLI emits fresh hash-bound files and rejects overwriting its output directory. This functional integration passes28.07 seconds under Go race. The helper runs only inside the test executable; no standalone helper or product was built. New v2 tests reject changed source/native clocks, bool timestamps, altered view rules, and preserve existing v1 cases. Collected evaluation and whole native package checks are recorded separately after execution.
Limits: No whole roadmap card completed. Formal RunPlan/RunIndex producer, actual original-source native REF selection CLI and complete confirmatory E2E remain required engineering. EXP04 final-input consumption and integration with RTE remain separate work. Synthetic qualification and baseline digest do not authenticate people, timing, labels, real service costs or permissions. No operating DB, paid call, deploy, product/helper build, commit or PR.
